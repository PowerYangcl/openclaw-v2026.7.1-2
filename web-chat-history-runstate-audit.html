结论摘要

「切换即中断」是客户端造成的，不是服务端。服务端全程没有收到任何 chat.abort（ChatPane.vue:2521 只有「停止」按钮会发；网关侧 abortActiveRunsForRestart 只在重启时用，src/gateway/server-close.ts:421）。真实机制是：切走后前一个会话的终止帧被前端过滤掉，结果没落到任何地方，运行态又没人收，于是「回复不见 + 输入框卡在生成中」。

要点：

  • 参考实现（ui/）在「非当前会话的 final」上有两道兜底：runId 命中就继续处理；处理不了也要把回复写进该会话的消息缓存。web 一道都没有。
  • web 的 loadHistory 没有请求版本闸，异步响应回来时不校验「是否仍是我这个会话」；慢环境下连点两个会话，即可把 A 的历史写进 B 的视图、并被深 watch 以 B 为键写进缓存。
  • 缓存命中路径早退不联网：上面那条毒缓存 + 「空列表也落缓存」会让会话在 60s TTL 内每次都空白，唯一出口是刷新按钮。这条与本轮的「历史不显示」直接对应。

两条链路怎么走

ui/（参考实现）

  1. chat.history（若网关广告了 chat.startup 则优先用它，遇到 unknown method 再回退）→ normalizeMessage → 渲染。
  2. 请求版本守卫 + 同键去重：chat-history.ts:82-106（beginChatHistoryRequest / shouldApplyChatHistoryResult）、:777-818（in-flight 复用）。迟到的响应绝不写进当前视图。
  3. 按会话的消息缓存：session-message-cache.ts；切换会话时 chat-state.ts:319-367 resetChatStateForRouteSession 先存旧的、再 restoreChatMessagesForSession 秒回，同时 clearLocalRun 清本地运行态。
  4. 跨会话事件兜底：chat-gateway.ts:156-177 —— 会话不匹配但 runId 属于自己发起的 run ⇒ 继续处理；否则对非当前会话的 final appendCachedChatMessage(...)，把回复写进那个会话的缓存后 return null。

web/（现实现）

  1. chat.history（limit:200, offset:0, maxChars:200000）→ normalizeMessage → 过滤「无正文且无媒体」→ 渲染。
  2. 客户端缓存 utils/chatMessageCache.ts（60s TTL）+ 深 watch 同步；historyHasMore/nextOffset 支持向上翻页。
  3. 运行态按会话分桶放在组件外（utils/chatRunState.ts），修的是「点拆分视图打断任务」那个老问题。

web 的四个缺口（修复前，含证据）

  1. 运行态 事件过滤只认 sessionKey：ChatPane.vue:2795-2803（chat）与 :2773（agent thinking）。切到 B 后 A 的 delta 与终止帧 final 一起被丢 → A 内存态没有回复、缓存也停在切换那一刻。
  2. 历史 loadHistory 无会话/版本守卫：ChatPane.vue:2188+ 在 await 之后直接 messages.value = ...。响应回来时若已切到 B，A 的历史进了 B 的视图；紧接着深 watch（:441）用当前 sessionKey 当键写缓存 ⇒ B 的缓存被写成 A 的内容（A 为空时就是空）。
  3. 历史 空列表也落缓存：深 watch 无条件 setChatMessageCache(key, [...list])；切到冷会话时 messages.value = [] 会先落一条空缓存（ts 刷新）。
  4. 历史 缓存命中即早退、永不回源（:2146-2157）⇒ ② ③ 造出的毒/空缓存在 TTL_MS = 60_000 内每次切进去都空白，一个请求都不发。这就是「历史消息不显示」最直接的放大器。

「切会话不中断前一个会话的执行」结论

修复前：不满足。服务端 run 没被中断（没有任何 abort 请求），但客户端把结果丢了 ⇒ 用户视角就是被中断。

可观测的连锁反应（修复前后都值得记住这条链）：

  1. A 的 final 被丢 → A 的回复不在内存、也不在缓存。
  2. A 的运行态桶里 sending 永远是 true：全仓只有 finalizeStreaming() 会清它，而它只在「本会话收到终止帧」时被调；resetChatRunState 此前无人调用。
  3. 切回 A：60s 内命中旧缓存 → 回复缺失；输入框停在「正在生成」，回车走 enqueuePendingTask() 而不是发送，而 scheduleNextPendingTask() 只在事件里触发 ⇒ 该会话直到刷新页面都用不了。

服务端侧的证据：ChatPane.vue:2521 abort() 仅由模板 @click="abort"（:4027）触发；web 全文没有 sessions.reset；网关只在重启时 abort 活动 run。

本次修复

1. 跨会话终止帧不再丢（对齐 ui chat-gateway.ts:156-177）

web/src/utils/chatMessageCache.ts 新增「后台会话终止回复暂存」：noteBackgroundAssistantMessage / readBackgroundAssistantMessages / clearBackgroundAssistantMessages（按稳定 id 去重、上限 20 条、clearChatMessageCache 连带清空）。
web/src/views/ChatPane.vue 新增 handleBackgroundSessionChatEvent：视图不动，但把非当前会话的 final 按会话 key 暂存，并顺手归零那个会话的运行态。
刻意不处理 aborted：引导（sessions.steer）会先中断当前 run，那一瞬间同会话的另一个窗格正靠 sending 撑着「思考中」气泡；在别的窗格里归零会让被引导轮的 delta 被 if (!sending.value) return 丢掉。被引导的那一轮结束时同样走 final。

2. 运行态按会话归零

web/src/utils/chatRunState.ts 新增 resetChatRunStateForSession(sessionKey, defaultAgentId)：只收干净已存在的桶（不新建），键与创建时同源。

3. loadHistory 加请求版本闸 + 尾部保留

每次请求自增 historyRequestSeq，await 之后校验「序号仍是最后一次 + 规范化会话 key 未变」，不满足整包丢弃；loadOlderHistory 同样加了会话比对。
新增 preserveLocalTailMessages（简化版对齐 ui/chat-history.ts:287）：请求期间本地 push 的乐观气泡 / 刚落库的回复，服务端结果里没有就追加回去 —— 这正是「缓存命中后继续回源」引入的竞态，必须一起堵。

4. 缓存策略：不缓存空、命中后静默回源

深 watch 遇到 list.length === 0 直接 return；缓存命中仍然先秒回，但不再 return，继续走一次服务端回源（stale-while-revalidate）自愈毒缓存；失败/迟到一律不落缓存。

5. 老网关入参降级（针对预发的一条已知成因）

ChatHistoryParamsSchema 是 additionalProperties:false（packages/gateway-protocol/src/schema/logs-chat.ts:30-39）⇒ 前端产物比网关新时，offset/maxChars 会让整条请求被判 INVALID_REQUEST: invalid chat.history params，一条历史都不显示。
新增 requestChatHistory：命中该错误就退化成 { sessionKey, limit } 再试一次（代价是拿不到 hasMore/nextOffset 与长正文放大，但历史能显示）。

真机验收（切走不中断）

  1. 在会话 A 发一条会跑几秒的消息（例：让它写个稍长的回答），保持气泡「思考中」。
  2. 点左侧栏切到会话 B，等 A 那条跑完。
  3. 切回 A：回复必须在（本次修复前会缺，或只在切回后再点刷新才出现）。
  4. 在 A 直接回车再发一条：必须直接发出（修复前因为 sending 卡住，只会进「待执行」队列）。

遗留与风险

  • 有意为之 切走后 A 的 delta 仍然丢弃（与 ui 一致）：回来时看不到「切走期间逐字生成」的过程，只保证最终回复在。要连过程都留住，需要把流式累积也按会话分桶（chatRunState 已有桶，但当前只在窗格挂载时写入）。
  • 性能 缓存命中后多一次 chat.history 请求（SWR 的代价），换来的是毒/空缓存自愈。
  • 降级 老网关降级路径拿不到 hasMore/nextOffset，「加载更早历史」在该网关上不可用（本来就是）。
  • 未覆盖 aborted 不做跨会话归零（原因见修复 1）；多客户端场景下若别的客户端 abort 了 A，本端切走时 A 的 sending 仍需切回后靠一次正常流式帧纠正。
  • 测试 pane-wechat-session.e2e.mjs 依赖 Vue 句柄，只能跑 dev 5273；生产基线请以 DOM/文本断言为准。
