OpenClaw Architecture Brief

Gateway 与 Control UI：同仓协作、两种运行模式

基于本仓库实际脚本与文档，说明本地 gateway-lite 联调、生产集成交付，以及前端独立部署时的收益、成本和选择边界。

pnpm monorepoVite + LitWebSocket RPCGateway :18789

先看结论

“同一个 monorepo”解决的是代码、协议、版本与交付协同；它不意味着开发阶段前后端必须运行在同一个进程。

同仓的核心价值Gateway 与 UI 共享协议演进节奏，能够在同一变更中完成后端方法、类型契约、前端调用和测试更新。
开发模式Vite 单独提供 UI 热更新，gateway-lite 只提供轻量 WebSocket 后端，并关闭 Gateway 内置 Control UI。
生产默认模式先构建 UI 到 dist/control-ui，再由 Gateway 在同一端口托管静态页面和 WebSocket API。
默认建议：保持同仓与集成交付。只有存在独立域名/CDN、独立发布团队、超大规模静态流量或严格故障域隔离时，再选择前端独立部署。

项目架构与运行模式

模式一：生产集成托管

Browser │ HTTP 静态资源 + WebSocket RPC ▼ Gateway :18789 ├── dist/control-ui ├── 类型化 WS API └── 鉴权 / 配对 / 策略

同源、同端口、单入口。安装、升级与回滚可按一个产品版本执行。

模式二：本地分离联调

Browser ├── HTTP ──▶ Vite :5173 └── WS ───▶ Gateway Lite :18789 ├── Control UI disabled └── Channels skipped

前端获得热更新体验；Gateway 通过 allowedOrigins 接受指定的 Vite Origin。

为什么放在同一 monorepo

共享契约packages/gateway-protocol、Gateway 方法和 UI API 可原子修改，降低协议错配风险。
统一工程入口根工作区统一提供安装、UI 构建、Gateway 启动、协议生成和测试命令。
单包交付UI 产物随 Gateway 版本分发，不需要维护额外的前端部署清单和兼容矩阵。
安全边界集中Token、密码、设备配对、代理身份与 Origin 策略集中在 Gateway 入口处理。
跨层评审一次变更即可完整呈现协议、服务端、客户端和验证影响，便于审查与回滚。
多客户端一致性Web UI 与 CLI、原生应用一样都是 Gateway 客户端，围绕同一类型化 WS API 演进。

本地启动：gateway-lite + UI 热更新

适用于日常前端开发与轻量联调。gateway-lite 会生成临时配置，不直接改写原配置；默认绑定 loopback、监听 18789、跳过 Channels，并关闭内置 Control UI。

1
安装依赖（首次）
pnpm install
pnpm ui:install
2
终端 A：启动轻量 Gateway
pnpm gateway:lite
3
终端 B：启动 Control UI
pnpm ui:dev
4
打开 Vite 输出的地址

当前 Vite 配置默认端口为 5173。若 Gateway 日志提示 Origin 不允许，请显式对齐 Origin 后重启：

OPENCLAW_FRONTEND_ORIGIN=http://localhost:5173 pnpm gateway:lite
端口注意：start-gateway-lite.sh 当前默认允许 http://localhost:5273，而 ui/vite.config.ts 当前默认使用 5173。应以实际 Vite 输出地址为准，通过 OPENCLAW_FRONTEND_ORIGIN 对齐。

可调整的环境变量

变量用途默认/说明
OPENCLAW_GATEWAY_PORTGateway 监听端口18789
OPENCLAW_GATEWAY_BINDGateway 绑定范围loopback；对外暴露前需评估安全策略
OPENCLAW_FRONTEND_ORIGIN允许连接的前端 Origin必须与浏览器实际访问 Origin 完全一致
OPENCLAW_CONFIG_PATH指定配置来源脚本基于其生成临时配置
OPENCLAW_STATE_DIR指定状态目录用于隔离本地运行状态

生产集成交付

构建与启动

pnpm install
pnpm build
pnpm ui:build
pnpm gateway:watch

UI 构建结果进入 dist/control-ui，Gateway 负责 SPA fallback、运行时配置、CSP 和受控资源访问。

关键约束

  • gateway:watch 不会自动重建 Control UI。
  • 修改 UI 后需重新执行 pnpm ui:build，或开发时改用 pnpm ui:dev。
  • 浏览器缓存旧 UI 或旧 Service Worker 时，可能与新 Gateway 发生协议不匹配。
  • 协议变更应同步服务端方法、UI 调用并按需执行 pnpm protocol:gen。
同仓不等于强耦合成一个源码模块：仓库仍通过 ui/、src/gateway/ 和协议包保持边界；集成发生在构建产物、协议版本与部署入口层面。

同仓集成交付 vs 前端独立部署

维度同仓 + Gateway 托管 默认前端独立部署 可选
协议一致性前后端可原子提交、测试和发布，错配概率低必须维护 API/WS 兼容策略、版本探测和兼容矩阵
本地开发同一工作区安装；仍可用 Vite + gateway-lite 热更新仓库更轻，但跨仓联调、契约同步和环境准备更复杂
发布与回滚Gateway 与 UI 单版本、单制品、同步回滚可独立发布和回滚，但需防止新 UI 连接旧 Gateway
部署复杂度一个服务入口，无额外静态站点、反向代理和部署流水线需要对象存储/CDN/静态站点、域名、证书及缓存策略
鉴权与安全同源入口，鉴权、设备配对、CSP 与访问策略集中需重新设计跨域凭证、Origin 白名单、代理信任和 CSP
CORS / 网络同源，浏览器限制少；HTTP 与 WS 路径清晰需处理 CORS、WebSocket Origin、代理升级和多域名网络故障
静态资源性能足以支撑控制面 UI，但静态流量由 Gateway 承担可使用全球 CDN、边缘缓存和静态资源专用优化
扩展与隔离UI 和 API 共用部署入口，模型简单但故障域一致静态站点与 Gateway 可独立扩缩容、限流和隔离故障
缓存风险版本随 Gateway 发布，但 Service Worker 仍需正确失效CDN 多层缓存增加旧 UI 命中新 Gateway 的概率
CI/CD 成本跨层检查集中；UI 改动可能触发更大流水线流水线自治且前端发布快，但需增加跨仓契约测试
团队协作适合共享产品目标、频繁跨层变更的小中型团队适合边界成熟、团队独立且发布节奏明显不同的组织
运维与可观测性入口、日志、版本和告警更集中故障定位需串联 CDN、静态站点、代理与 Gateway
总体成本工程与运维成本较低，产品交付路径短灵活性更高，但治理、兼容、安全和基础设施成本更高

以上为定性比较；实际性能与成本取决于访问规模、地域分布、缓存策略、组织结构和基础设施能力，不应脱离压测与运行数据给出固定数字。

如何选择

优先同仓 + 集成交付

  • UI 是 Gateway 的控制面，而非独立公众产品
  • 前后端协议变化频繁
  • 重视开箱即用、离线/本地运行和单包升级
  • 希望降低部署、安全与运维复杂度
或

考虑前端独立部署

  • 静态流量规模需要 CDN 和边缘分发
  • 前端拥有独立团队、域名、SLA 和发布节奏
  • 必须隔离 UI 与 Gateway 故障域
  • 愿意投入版本协商、跨域鉴权和契约治理

若选择独立部署，至少补齐

契约治理协议版本握手、兼容窗口、生成客户端与跨版本集成测试。
安全设计明确 Token 传递、设备配对、Origin 白名单、CSP、TLS 与代理信任边界。
发布防护灰度、可回滚制品、CDN 缓存失效、Service Worker 更新与旧版本熔断。
