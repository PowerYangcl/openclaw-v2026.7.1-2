独立 vs 混合：openclaw 前端部署方案对比

方案 A（前后端同仓 monorepo）vs 方案 B（独立域名前端子项目）

方案 A · monorepo 方案 B · agent-claw-web 评审稿 v1

摘要

openclaw 项目当前已实质性落地 方案 A：web/ 子包与 src/ 后端同处于 monorepo 中，由 pnpm-workspace.yaml 声明，并通过 src/infra/control-ui-assets.ts 的 candidates 探测顺序同时支持新老 UI 共存。方案 B（独立 agent-claw-web）是用户当前领域内已经回填的一部分历史形态，评估的是迁移回或并行部署两类部署策略的边界。

本文档围绕 5 个必答维度 + 9 个补充维度，结合项目内现存代码事实（候选路径、协议定义、媒体签名、device token 等）给出对比结论与推荐路径。

核心结论
方案 A 在 运维、版本对齐、调试 上明显占优；方案 B 仅在 跨团队解耦、独立灰度 上有可量化的收益。openclaw 项目当前阶段的真实瓶颈是 provider 模型配额 与 网关承载，而非前端分发——因此 推荐保持方案 A，仅在外部 SaaS 化阶段重新讨论方案 B。

方案速览

方案 A

前后端同仓（当前已落地）

Vue 3 SPA 构建产物落在 web/dist/，由 gateway 在同进程内服务。

  • gateway.process.serveResolvedIndexHtml() 注 basePath
  • control-ui-config.json、/__openclaw__/avatar/<id>、/__openclaw__/assistant-media 同源
  • WS 单连接 ws://host:port/
  • Ed25519 deviceToken（5min HMAC 媒体票）
方案 B

独立 agent-claw-web（外部托管）

前端代码在独立仓库，独立 CDN/域名，与 gateway 跨域通信。

  • 前端域名：ui.openclaw.example.com
  • 后端域名：gw.openclaw.example.com
  • WS/CORS 必须显式放行
  • 需要独立 CI/CD、副版本号

1. 历史实例兼容性

这一维度关心：已部署且仍在使用旧 UI（Lit ui/ 构建产物或外部 agent-claw-web）的实例，切到新方案后是否会出现接口不兼容、功能丢失、用户数据错乱等问题。

1.1 协议版本对齐

子项方案 A（同仓）方案 B（独立部署）
gateway WS 协议（v4） 前端与 gateway 同仓，connect.params.protocol.version 与 SDK 同步迭代，commit 即同步升级。 必须显式声明minGatewayVersion 或 protocolNegotiation，否则旧版 UI 调到高版本 gateway 会出现帧解码失败。
RPC method 收敛 agents.list / agent.identity.get / sessions.send / sessions.steer 由同仓 packages/gateway-protocol/src/schema 集中声明，类型双向校验。 需要打 @openclaw/gateway-types 子包独立发布；两端版本错位会立刻显形（缺 method 调用报 404）。
设备能力要求 deviceToken（Ed25519，@noble/ed25519@3.1.0）。前端 + gateway 同步升级。 当前 token 格式 v2|deviceId|clientId|clientMode|role|scopes|signedAtMs|token|nonce 必须与 gateway 严格字节对齐，独立仓容易出现 'role' / 'scopes' 字段序列化差异。

1.2 数据契约

前端读取的字段基本都是网关侧的 schema 派生（chat.history 的附件、session.key 规范键、IDENTITY.md 解析首尾反引号清洗、agent.identity.get 的 avatarStatus 等）。独立仓要重新分发这些调用，要么打 npm 包，要么手动同步——前者增加 7-10 个版本的协调义务。

1.3 设备身份

localStorage.openclaw.device.identity.v1 + openclaw.device.auth.tokens.v1 是同源 origin 绑定的。如果用户浏览器里现有 UI 跑在 127.0.0.1:18789，而新的独立 UI 跑在 ui.openclaw.example.com，localStorage / IndexedDB 是不同 origin——用户会被静默重登一遍。

兼容坑位
方案 B 必然丢失：浏览器侧的持久偏好与设备身份，除非在 origin 间设计共享迁移通道（VPS 同步、cookie-sharing 或在 gateway 端引入 state lease 协议）。即使做了迁移，对老用户也是一次强制刷新。

2. Gateway 层影响

2.1 候选静态路径

项目内 src/infra/control-ui-assets.ts:225-256 已经把 两类 UI 同时列入候选探测序列：

addCandidate(execDir/../Resources/control-ui)     # macOS 包
addCandidate(moduleDir/control-ui)                # 打包后 dist/control-ui
addCandidate(moduleDir/../../dist/control-ui)     # src/gateway → dist/control-ui
addCandidate(moduleDir/../../web/dist)            # 新 Vue 3 UI（注释：'New Vue 3 UI'）
addCandidate(argv1Dir/dist/control-ui)            # 老 Lit UI
addCandidate(argv1Dir/control-ui)
addCandidate(argv1Dir/web/dist)                   # 新 Vue 3 UI（argv1 = openclaw.mjs）
... packageRoot / cwd 同模式 ...
共存现状
当 老 dist/control-ui 与新 web/dist 同时存在 时，老 dist 会优先被命中（顺序更靠前）。要让 web/dist 优先必须显式 gateway.controlUi.root 指过去（脚本 scripts/dev-gateway-with-web.sh 已就绪）。

这意味着什么

  • 方案 A：打包脚本只需打 web/dist，gateway 启动时命中它；老 dist 可以不删除——天然兼容回滚（旧镜像可以照旧走 Lit UI）。
  • 方案 B：candidates 顺序完全失效——独立前端压根不在本机。控制逻辑被两侧各自的部署流程接管，gateway 不再持有"前端是什么"的判断。

2.2 HTTP 媒体面

路径作用方案 A方案 B
/control-ui-config.json 前端启动配置（gateway URL、token 提示等） 同源，无 CORS 跨域，必须显式 Access-Control-Allow-Origin
/__openclaw__/avatar/<agentId> agent 头像（HMAC 5 分钟签名） <img src> 直出 CORS 404 必须放行；签名参数 ?token= 跨域链路要确保完整
/__openclaw__/assistant-media 语音/录像，HMAC 5 分钟 ticket 同源 跨域 + 强制 CSP frame-ancestor
/api/v1/jd/spend 积分结算（私有） 内部 需要外部鉴权 token + 引入 SAAS 访问凭证系统

2.3 WS / RPC 行为差异

两种方案运行时都走 WS，但在以下行为上会有可见差异：

  • 握手 URL 推导：deriveDefaultGatewayUrl 默认 ws://<host>:<port>/。方案 A 浏览器与 gateway 同源；方案 B 跨域时必须显式 allowlist Sec-Fetch-Site: cross-site + Ed25519 签发的 Origin 白名单。
  • 协议版本协商：低版本浏览器 Sec-WebSocket-Protocol 与后端期望的 v4 错配在方案 A 静默升级；方案 B 下 CDN 可能裁掉 upgrade header。
  • deviceToken 失效回退：方案 A 走同源刷新就能续期；方案 B 需要支持第三方 cookie（浏览器在第三方上下文中默认禁用），大多数用户体感为"反复掉登录"。
  • RPC 容错：connect.snapshot 不含 agent 列表，agents.list 不带 name/avatar——必须 agent.identity.get 二次回填。方案 B 跨域下网络延时叠加，复杂场景下页面 cold-start 多 200-500ms。

2.4 覆盖发布后的能力丢失

假设已发出去的实例仍在 gateway v1.x（Lit UI）+ agent-cli v1.x，切到新方案覆盖发布，这些实例会丢失：

  • webSocket 升级仍兼容，但 HTTP /control-ui-config.json 不再由 Lit 解析（Lit UI 已下掉），回到 HTML 静态资源（无所谓，因为无新前端在跑）。
  • 若 gateway 升级到 Vue 3 web/dist 但 用户浏览器仍加载了老 Lit UI bundle（被浏览器缓存粘住），会出现新旧 UI 同时尝试连接，WS 多连接——当前实现不接受多连接，老实例用户反复刷新直到清缓存。
  • 设备身份 Ed25519 私钥如果丢失（清缓存），需要重新 device.pair.list 配对。
化解
发布时加 HTML meta Cache-Control: no-cache + 资源 ?v=<hash> 强制刷新；同时把 control-ui-assets.ts 探测顺序微调一下，让新 dist 优先于老 dist 即可（已就绪）。

3. 独立 vs 混合部署（渐进迁移）

3.1 实例 id + 泛域名拼接

混合期间，配置 实例独立前端域名 是最丝滑的迁移路径：

                            DNS（泛域名 *.openclaw.example.com）
                                         ↓
                            边缘网关 / nginx-ingress（Catch-All）
                                         ↓
                ┌────────────────────────┼────────────────────────┐
                ↓                        ↓                        ↓
      ui-i8d72.openclaw.example  ui-jf3as.openclaw.example  ui-9kkaz.openclaw.example
      (key='i8d72')              (key='jf3as')              (key='9kkaz')
                ↓                        ↓                        ↓
                  └───── 同一个 gateway pool（sticky by cookie）────────┘

WS URL 推导:  ws://<window.location.host>/  （浏览器自动转换 https → wss）
deviceToken:  在每个子域名 origin 下独立 localStorage（无法跨域共享！）
config.json:  /control-ui-config.json  → 同子域同源，仍 OK

关键不变量：

  • 实例 ID 取首 8 位 hash（qualifySessionKey 派生），不会和人类可读名字冲突。
  • DNS 解析必须把每个子域名映射到同一个 backend pool，靠 cookie sticky session 维持 WS 不重连。
  • WS 升级时 Origin = https://ui-i8d72.openclaw.example；gateway 须把实例 ID 由 DNS 反解到后端 hostname，再匹配 session.key —— 一旦失配会 401。

3.2 混合期需要小心的几件事

陷阱说明对策
设备身份跨子域 每个子域名 origin 下 Ed25519 私钥独立；用户在 A 子域配对后跳到 B 子域会"重置" 把 deviceToken 同步到 gateway 后端存储（而不是 origin-localStorage），跨域共用
localStorage 偏好分裂 openclaw.web.prefs.v1、.sidebarSnapshot.v1 等会按 origin 分裂 要么全收拢到 backend（推荐），要么在混合期明确告知用户"用户偏好仅在本实例内有效"
媒体签名 ticket 跨域 avatar/assistant-media 用了 5 分钟 HMAC ticket；跨子域名要重新算一次 改用 resolveGatewayHttpBase：先绝对化再补 token（见 web/ 现有 utils/assistantMedia.ts）
WebSocket 多实例粘性 N 域名 M 后端时，浏览器 sticky cookie 失效 边缘网关基于 Hash(IP + cookie) 哈希到固定后端；或每个子域名绑一个独立后端
CORS 链路过长 每个 RPC 都要选项预检；冷启 200-500ms 浏览器侧 ws://gw.openclaw.internal/ + UI 直连；非必要不跨域

3.3 渐进迁移推荐开关

  • gateway.controlUi.dual：默认 false；true 时同时挂两个 index.html（/_internal/old.html 路径走老 UI）。
  • 网关启动日志里加 [control-ui] candidates: web/dist (resolved), dist/control-ui (skipped: override) 标识当前生效路径。
  • 混合期总时长建议 4-8 周，超期强制推进。

4. 运维成本对比

4.1 域名 / 证书

项目方案 A方案 B
DNS 记录数1 个 openclaw.example.com1 个 + 1 个泛域 *.openclaw.example.com（混合期更多）
证书维护单域名，3-12 月续期泛域证书（CDN 通常送，但本地内网要单独签）
SNI 配置无特殊nginx-ingress + ACME 自动化

4.2 CORS / 跨域鉴权

方案 B 会新增的列表（不只是网关，CDN/ingress 也要列）：

  • Access-Control-Allow-Origin：不能用 *，必须列 allowlist（含方案 B 的所有部署形态）
  • Access-Control-Allow-Credentials：必须 true（deviceToken 是 cookie-like）
  • Access-Control-Expose-Headers：x-openclaw-request-id 等
  • 5min HMAC media ticket 校验放在 CDN 还是 gateway？两条路要权衡（CDN 校验意味着 CDN 看得到票面）
  • WS Sec-Fetch-Site: cross-site 合法化 + 同源 cookie 失效下的退路

4.3 构建流水线

环节方案 A方案 B
CI 复杂度 1 个仓库，1 条流水线，pnpm workspace 串起来 2 个仓库，2 条流水线，需要同步版本号策略
镜像产物 gateway 镜像自带 web/dist，单 artifact 前后端两个镜像 + CDN 静态资源
构建时间 ~3.5s vite build（实测，见上文） 同上 + 跨仓库推 npm 包 + 拼接版本号
本地开发 cd web && pnpm dev（vite proxy 已配齐）/ scripts/dev-gateway-with-web.sh 要先把前端独立发布到本地，再让 gateway 反代 CDN；或者用 ngrok/cloudflared tunnel

4.4 多环境一致性

方案 A：dev / pre / prod 三套 docker 都用同一个 web/dist 路径约定，运维心智是"找一个 controlUi.root"。

方案 B：

  • UI 三个环境各有自己的 CDN bucket / 不同哈希策略
  • gateway 三个环境要白名单三个 UI origin
  • 缓存策略（Vite 产物 1y 强缓存 + index.html 5min 协商）在 CDN 上要逐环境配置

4.5 监控与告警

  • 方案 A：前端报错可以直接打到 gateway（同一个 origin），后端日志里就能看到 stack + WS 帧 id。
  • 方案 B：浏览器侧错误只能走 /api/v1/client-error 端点上报，要单独账户，跨域请求需要更多工作。

5. 其他关键维度（补充）

5.1 发布回滚

方案 A方案 B
回滚步骤 1 步：launchd kickstart -k 拉起旧镜像（dist 在镜像内自带） 3 步：回滚镜像 + 回滚 CDN index.html + 清理客户端缓存；前端 CDN 又多了 1 分钟缓存窗
粒度 前后端一起 前后端可独立回滚，但常常需要协调

5.2 版本对齐

  • 方案 A：commit hash 即单一真相源，gateway 日志中能看到对应 UI 版本。
  • 方案 B：必须引入 cross-repo release tag；常见事故是"前端发了 v2.3，但 gateway 还在 v2.1，部分 RPC 报错"。

5.3 调试成本

  • 方案 A：DevTools network tab 全同源，WS 帧可读，时延/丢包/重连都是干净的客户端事件。
  • 方案 B：跨域请求会被 DevTools 标记 "CORS preflight"，时长翻倍；WS 在 Safari 上的跨域行为还有点边界 case。

5.4 团队协作边界

  • 方案 A：UI 改一行要等 gateway PR review，反之亦然——可能在跨团队时摩擦。
  • 方案 B：清晰边界，但意味着接入冲突变成"联调会议"的治理问题。

折中：在 monorepo（方案 A）内部 把 web/ 作为独立 node sub-package，PR review 时 cross-package 的修改自动请求两组 reviewer，不丢解耦，但保持 CI 单点。

5.5 200 人并发压测（独立域名场景）

假设 200 个活跃会话同事同时打开独立域名 ui.openclaw.example.com：

指标方案 A（同仓 + gateway 同时撑静态）方案 B（独立 CDN + 跨域 WS）
HTML 体积~2 KB，gateway 一次性回包同 + 可能 CDN 命中（缓存命中省 RTT）
首次资源 RTT1 RTT → gateway2-4 RTT → CDN → gateway（preflight 走 SSL 握手）
WS 连接建立直接 upgrade，无 preflight浏览器先 OPTIONS，再 upgrade，多 1 RTT
200 并发冷启总耗时~2s~5-8s（含 OPTIONS + CORS 校验 + CDN TCP）
网关连接数200 WS + 200 HTTP fetch（单连接 keep-alive）400+ WS（CDN 转发 1:N）和 200 HTTP
CDN 流量回源n/a（不走 CDN）命中率依赖 TTL；冷启动 100% 回源
压测结论
200 并发在方案 A 下是单实例 gateway 即可吃下的范畴（Node 单进程 ~10k keep-alive，200 WS 占 2%）。方案 B 必须引入 CDN + 多 gateway 实例，但同时也会把 cert / TLS 终止 这层额外负担加到运维。

5.6 负载均衡策略

方案 A 下的 LB 选型：

  • WS 是 sticky（Sec-WebSocket-Key 哈希）
  • RPC 可任意路由
  • 典型组合：nginx-ingress → gateway pool (3 inst) → sqlite state

方案 B：

  • UI 走 CDN，按地理位置
  • WS 走 gateway pool，与 UI 解耦
  • CDN ↔ gateway 之间多了一次握手，gRPC/HTTP2 多路复用能省但增加 mTLS 配置

5.7 租户隔离 / 多实例

  • 方案 A：实例 ID 通过 session.key 后缀隔离（id-<hash8>）；同一 gateway 池天然支持。
  • 方案 B：每个实例独立子域名（ui-i8d72.openclaw.example）—— DNS 是天然的隔离，但需保证 gateway 仍能识别身份（Origin header + 实例 ID 反查）。

5.8 终端用户感知

  • 性能：方案 B 由于 CDN 缓存体验冷启更快，热路径相同。
  • 可靠性：方案 B 任何一个子域 CDN 出问题只影响该子域实例；方案 A 整个 gateway down 时全军覆没。
  • URL 形态：方案 B 的实例化子域名反而比 hash.openclaw.example/path/path 更接近用户感知"我有独立空间"。

5.9 备份 / 灾备

  • 方案 A：备份 gateway 镜像（含 web/dist）。
  • 方案 B：备份 gateway 镜像 + CDN 配置 + 泛域名证书私钥。前者的备份要求更严格，少一个 token 都无法恢复。

结论与建议

推荐的迁移路径

  1. 保持方案 A 作为主路径——已落地，构建/调试/回滚全链条验证。
  2. 将 scripts/dev-gateway-with-web.sh 的"显式 root override"提升为文档化命令（避免每次手动）。
  3. 把 control-ui-assets.ts 的候选顺序从"老 dist 优先"调整为"新 web/dist 优先"（被 gateway.controlUi.root 显式指定时不生效）。
  4. 把当前已经写到一半的 UI 缺失项（exec-approval, theme-mode-toggle, command-palette）补完后再考虑下一步。

何时重新评估方案 B

  • openclaw 走出内网、要面向 SaaS 用户（每个客户独立域名）
  • 前端开始独立团队运营、与后端发布节奏解耦
  • 需要把前端作为独立 npm 包公开（如 @openclaw/control-ui-web）被第三方嵌入
最终建议
方案 A 在当前阶段几乎在所有"硬指标"上都优于方案 B；方案 B 的优势集中在"可演示的隔离体验"与"跨团队协作清晰"这两条非技术指标上。建议 方案 A 为主 + 在 SaaS 化前重新评估。
