01 · 结论

推荐 方案 A

选方案 A：前端并入 openclaw 仓，作为 pnpm workspace 成员 web/，与网关同源部署。

一句话理由：前端与网关之间是硬契约耦合（WS 协议 v4 帧结构、ed25519 设备握手、 会话 key 规范形态、RPC 方法集），只有同仓才能靠 packages/gateway-protocol 的 类型把契约钉在编译期。方案 B 把这些契约手工复制成 1301 行副本，没有任何 CI 能发现漂移—— 今天修的 P0（所有 chat/agent 事件被丢弃 → 永久卡「思考中」）就是契约理解不一致造成的。

另一条同样重要的理由来自本次重构的直接动因（详见 02 节）：内置 UI 层 25 万行、 一个「积分」功能点散落在 32 个文件里、改一行就要重新构建并重新装载插件。 这类效率问题只有在可读、可热更新、契约可被类型守护的 Vue 工程形态里才能真正解掉， 否则换了框架也只是把同样的困难搬个位置。

「面向 C 端」这一前提进一步强化了方案 A。C 端最不能接受的是 「用户遇到功能突然不可用」，而本项目的网关对陈旧 UI 客户端是握手硬拒 （protocol mismatch → close(1002)）。方案 B 的前端在 CDN / 浏览器里是 缓存态、无法强制刷新，网关一旦演进协议就可能让部分旧用户 连都连不上；同时独立域名还会新增一整条 C 端接入链路（DNS / 证书 / LB / CDN） 及其长期运维与压测成本。方案 A 把前端并入网关镜像后，这两个成因都不存在。

⚠️ 决策前提：A 和 B 目前是同时在跑的，必须收敛到一份。

方案 A 已经落地（pnpm-workspace.yaml 的 packages 里已含 web， web/INTEGRATION.md 记录 2026-09-13 完成 Vue 3 迁移）；方案 B 也在跑 （agent-claw-pre.jdcloud.com）。现状成本是实的：为修一个 bug， ChatView 的改动在两处各做一遍，本次手工同步了 3 轮（事件隔离修复 → 思考标签去重 → 上下文口径 + 弹层结构 + 29 条单测 + 2 个 e2e），且只能靠人保证不漏。

02 · 重构动因：一次「修改积分」暴露的结构性成本

这次动手改的是积分（spend / balance）相关功能——即每条 AI 回复下方那行 「已消耗 X 积分 · 剩余 Y 积分」，以及「积分计算中」「积分不足」的提示逻辑。 在新 Vue 前端里，这是一处位置明确、可直接定位的功能；但在 openclaw 内置的 UI 层里， 它成了一次代价很高的排查，也正是本次重构的直接起因。

2.1 问题从「定位改动点」这一步就卡住了

内置 UI 层是 ui/ 目录下的 Lit 3 web-component 实现 （lit@3.3.3）：页面被写成自定义元素，视图由 TypeScript 里的 render() 返回模板字符串，样式另放在全局 CSS。换句话说， 功能边界既不在目录结构里，也不在文件命名里——想改一个功能点， 必须先靠经验猜「它可能属于哪个自定义元素、被谁监听、状态存在哪儿」。

  • 规模先劝退：ui/src 共 512 个文件 / ​254,359 行 TS·JS·CSS，其中 pages/ 234 个、lib/ 105 个、 i18n/ 89 个；42 个文件里定义了自定义元素。 — find + wc -l + grep customElements.define
  • 单文件体量极大：pages/workboard/view.ts 2,908 行、pages/chat/components/chat-message.ts 2,733 行、pages/chat/components/chat-composer.ts 2,405 行 …… 一个功能点往往就埋在某份三千行文件的模板字符串里。 — wc -l
  • 「积分」一个功能点，逻辑散落在 11 个非 i18n 文件里 （app/overlays.ts、app/router-outlet.ts、styles/layout.css、 lib/workboard/index.ts、pages/chat/components/chat-message.ts、 pages/chat/chat-thread.ts、pages/usage/view.ts、 pages/config/quick.ts、pages/skill-workshop/view.ts 等，含 1 个 e2e 用例）， 另外还要同步 21 个语言的 i18n 文件——合计 32 个文件。 — grep -ril "spend|积分|credit" ui/src

结论：人肉 grep 在这里几乎失效。一次检索动辄命中几十个文件， 其中大部分是「看起来沾边、实际不是你要改的那处」，只能靠通读来排除。

2.2 于是只能让 AI 全量读取 —— 然后它就崩了

既然精确定位不了，就只能换策略：把相关目录整体交给 AI 读， 让它自己找出改动点。这条路在 25 万行量级上直接失效：

  • 上下文被撑满：单是 pages/chat/ 连同它依赖的 lib/ 与 i18n/，就远超一次可用的上下文窗口，只能反复切分、反复重读。
  • AI 多次崩溃：读取量过大时任务中断，此前建立的上下文全部作废， 只能从头再读一遍才能继续——这是一个会反复发生的循环，不是一次性损耗。
  • 本机被拖垮：大目录的文件扫描与索引把内存和磁盘 IO 打满， 期间出现过电脑死机，开发进程被反复打断。
  • 改完还得重新构建：ui/ 的改动要重新 build 才生效， 随后还需重新装载本地安装的插件——「改一行 → 看到效果」的循环非常慢， 而这个慢是每一轮都要付的。

这不是「某个功能难改」，而是技术栈与工程形态造成的结构性成本。 定位成本 × 全量重读成本 × 构建装载成本，三者相乘才是效率崩溃的真正原因。 换一个人、换一个功能点，同样的剧本会再演一遍——这才是必须重构的理由。

2.3 重构为 Vue 之后，维护难度为什么显著下降

痛点 内置 UI 层（Lit web-component，ui/） 重构后（Vue 3 SFC + Pinia + Vite）
定位改动点 功能边界不在目录与命名里；模板是 render() 里的字符串， 搜一个功能要在 42 个自定义元素、32 个文件之间「拼图」。 一个文件 = 一个组件：views/ChatView.vue 的 <template> 就是完整 DOM 结构，功能点一眼可见；目录按页面切分，命名即边界。
AI 辅助成本 无法精确检索 → 只能整目录喂给模型 → 上下文撑满、多次崩溃、崩溃后从头重读。 改动点可收敛到单个 .vue 文件 + 对应 store， 读取量降一个数量级；<script setup> 中逻辑与模板同处一文件，一次读取即可完整理解。
反馈循环 改完必须重新 build，再重新装载本地插件，验证一轮很慢。 Vite 开发服务器提供秒级 HMR，保存即见、无需整包重建； 纯逻辑单测（esbuild 直跑）与 CDP 冒烟可独立执行，不必全量构建。
多语言文案 改一处积分文案要动 21 个语言文件，且极易漏改。 文案直接写在组件模板中，改动面从 21 处收敛到 1 处。 注：当前 Vue 版尚未引入 i18n，未来若需多语言再统一抽取，属一次性投入。
状态与数据流 状态散落在各自定义元素的私有字段里，靠事件冒泡串联，链路隐式、难追。 Pinia store 集中管理（useGatewayStore / useSettingsStore / useAgentsStore），数据流显式可追溯。
上手门槛 / 协作 Lit 生态小众，自定义元素 + 模板字符串的写法需要专门学习， 非前端同学基本无法参与。 Vue 是前后端开发者更熟悉的栈：SFC、props / emit、 v-if / v-for 属行业通用知识，后端同学也能直接改前端页面， 协作成本与上手成本同时下降。

2.4 更重要的是：为后续扩展与定制化铺路

本次重构不只是「换一个框架」，而是把扩展成本从「读 + 猜」降到「读一个文件」：

  • 新增页面 / 功能是增量的：在 views/ 加一个 .vue、 在 stores/ 加一个 store 即可，无需改动既有实现，回归面可控。
  • 定制化有明确落点：需要客户专属的聊天页样式、专属的积分展示规则， 都能在对应组件内局部完成，不必牵动公共代码。
  • 契约与 UI 分层清晰：网关协议由 packages/gateway-protocol 负责， UI 层只负责消费类型——这正是后文支撑方案 A 的关键前提。
  • 可测试、可回归：纯逻辑（如上下文占用口径）可写成不依赖浏览器的单测， 页面行为可用 CDP 端到端脚本守护，重构之后回归有据可依。

这段动因可以归纳为一句话：内置 UI 层的问题不是「写得不好」，而是 可读性差 + 代码体量大 + 构建反馈慢三者叠加，使维护成本随功能数量持续放大； 而 Vue 的「单文件组件 + 显式数据流 + 秒级热更新」恰好逐条解掉这三件事。 因此本次重构既是修复当下的效率问题，也是后续扩展与定制化的必要前置工作。

04 · 逐维度对比

前置前提：本产品面向 C 端。因此下表的权重是按 C 端的标准给的 —— 优先看可用性、灰度期间用户能感知到的差异、前后端版本一致性、接入层的运维与容量成本， 而不是「开发同学改起来方不方便」。其中「网关改动后新镜像已上、旧实例没有新功能」 是 C 端多实例部署下必须正面回答的问题：多实例 + 灰度/滚动发布意味着 同一次发布期间线上会同时存在新、旧两代实例，用户请求落到哪一代不由前端决定。

维度 A · 同仓 monorepo（openclaw/web） B · 独立仓（agent-claw-web） 判断
协议契约守护 可直接 import packages/gateway-protocol，类型即契约；网关改帧结构 / 加方法时，TS 全仓报错。 手工复制 1301 行，无任何 CI 能发现漂移；只能人肉比对 + 真机冒烟。 A 显著优
前后端协同 一个 PR 同时改前后端（例：加 sessions.queue 时前端同 PR 接上）。 跨仓两个 PR + 版本对齐；前端先上会打到旧网关，网关先上前端没接。 A 显著优
部署 / 跨域 网关托管 web/dist，同源——无 CORS、无 WS origin 白名单问题。 独立域名，需网关 gateway.controlUi.allowedOrigins 白名单 （不匹配则 checkBrowserOrigin 返回 origin not allowed， 以 INVALID_REQUEST 拒绝）。现已配通，但每新增一个入口域名都要再配一次。 — src/gateway/origin-check.ts:79 A 略优
UI 组件库 element-plus 开源，可随 openclaw 一起对外发布。 @jdcloud/mobius 内部包，与上游分叉；开源 / 外部部署受限。 A 优
发版节奏 跟随 openclaw 发版；前端小改动也要走网关发版流程。
C 端下这一条被放大：网关发布是大动作（滚动重启、连接重建、需回归验证）， 改一行文案也要触发它。		 独立发版，改文案 / 样式随时上，不用等后端 —— C 端活动页 / 文案迭代的关键。 B 优
回滚粒度 需回滚整个网关产物（或切回 legacy ui/）。 前端独立回滚，秒级，不影响网关。 B 优
新旧实例
版本一致性
（C 端关注）		 前端产物随网关镜像一起发布，前后端版本天然对齐。灰度/滚动期间旧实例是 「旧前端 + 旧后端」，因此降级是自洽的 —— 不会出现前端调用了旧网关没有的 RPC。
代价：灰度窗口内落到旧实例的用户「刷新也看不到新功能」； 需靠会话粘性 / 会话状态共享避免同一用户在实例之间跳变（网关会话落 sqlite， 多实例是否共享需确认）。		 前端独立发版 → 新功能立刻全量可见，不受网关镜像灰度节奏影响。 这正是解决「新镜像已上、旧实例没新功能」的直接手段。 各有取舍
版本 skew 风险
（前后端不同步）		 不存在：同镜像发布，前后端永不错配。 结构性存在，且对 C 端最危险：前端从静态托管/CDN 生效是 秒级全量，而网关灰度是分钟～小时级，两者节奏差 1～2 个数量级。 前端先上 → 打到未升级的旧实例会缺 RPC / 缺帧字段；网关先上 → 新能力无人使用。 C 端实例多、灰度窗口长、用户基数大，skew 的暴露面被显著放大， 且 C 端用户不理解灰度，只会表现为「功能坏了」。 A 显著优
运维成本
（长期持续）		 零新增：复用网关已有的域名、HTTPS 证书、发布流水线、监控告警； 网关侧只维护静态托管 + web/dist 目录。 一整套新增：独立域名（DNS 解析）、独立 HTTPS 证书（含续期）、 独立静态托管 / CDN、独立部署流水线与回滚、独立监控告警、 以及网关 gateway.controlUi.allowedOrigins 白名单的逐环境维护。
注意这是长期持续成本，不是一次性投入。		 A 优
负载均衡 前端走网关既有入口：直接复用网关已有的 LB / 多实例 / 健康检查， 不新增接入层，也不新增一个 C 端故障点。 多出一条独立接入链路：独立域名需要自己的 LB、证书与健康检查， C 端量级下还需多可用区部署。
而 WS 仍然打到同一个网关 —— 即 B 是「多一条链路」，不是「换一条链路」。		 A 优
压力测试
范围		 压测口径 = 网关（含 WS）。网关侧 WS 专项压测在 A / B 下都必须做 （见右栏列举项）。A 的额外工作≈0，静态资源由网关路由直出； 但需补一项：把静态文件纳入网关的连接 / 带宽预算，避免与 WS 争用。 在网关压测之外，额外需要：
  • 独立域名接入链路（DNS / LB / CDN / 证书）压测
  • 前端静态资源的 C 端并发压测
  • 混合版本组合测试：新前端 × 旧网关、旧前端 × 新网关

⚠️ 无论 A 还是 B，WS 专项压测都必须做（WS 都打到同一个网关）： 长连接数、连接建立速率（ed25519 握手是 CPU 密集）、心跳与 LB idle timeout 的匹配、断线重连风暴（C 端批量重连会打爆网关）、 会话粘性 / 亲和验证。		 A 优
静态资源
扩展能力
（C 端高并发）		 静态资源由网关实例直接吐出，与 WS 共用同一批实例的进程与带宽， 横向扩展受网关实例数约束。 独立域名可挂 CDN / 对象存储，静态资源脱离网关横向扩展， 不受网关实例数限制。
（A 也可以在网关前加 CDN + 回源获得类似扩展性 —— 属部署层优化，不改变代码归属。）		 B 优
权限 / 团队边界 同仓，前端同学可见后端代码（也可能构成干扰）。 独立仓，权限边界清晰，适合外部 / 跨团队协作。 B 优
迁移 / 切换成本 迁移已基本完成并通过冒烟；剩协议依赖化 + CI 门禁。 已在生产运行，有稳定入口域名与既有流水线 —— 但保留它就需要继续维护两份。 各有存量
双份维护
（A+B 并存现状）		 这是当前最大的实际成本：同一个 bug 要在两处各改一遍。今日实测：一个「事件隔离用错比较函数」的修复， 连带上下文口径、弹层结构、29 条单测、2 个 e2e 脚本，手工同步 3 轮，且无机制保证不漏。 两者皆痛
方案占优维度核心风险
A 同仓 契约守护、前后端协同、同源部署、UI 库开源、无版本 skew、零新增运维、复用网关 LB 前端发版被网关节奏拖慢（C 端下被放大）；回滚粒度粗； 灰度窗口内旧实例用户看不到新功能；静态资源与 WS 争用网关实例资源
B 独立仓 独立发版、独立回滚、权限隔离、新功能秒级全量可见、静态资源可 CDN 横向扩展 协议漂移无 CI 守护（今日 P0 成因）；跨仓协同； 版本 skew 在 C 端被放大（秒级前端 vs 分钟级网关灰度）； 新增一整条接入链路与长期运维成本（DNS / 证书 / CDN / LB / 压测 / 监控）； 双份维护

06 · 与网关的对接方式

前端要接上网关，共 7 个对接面。两种方案的差别不在「能不能通」——两边的 WS 都能通， 差别在每个对接面的耦合方式：A 靠类型在不同包之间传递契约，B 靠手工复制 + 配置。 其中 ⑦ 协议版本闸门是 C 端场景下最关键的一条：它不是"体验变差"，而是 连接被直接关闭，且无法靠前端代码补救。

6.1 对接面清单

对接面 A · 同仓 B · 独立仓
① 静态资源托管 网关托管 web/dist，访问 http://<gateway-host>/，同源。 京东云静态托管，访问 https://agent-claw-pre.jdcloud.com/，与网关异源。
② WS 端点 同源推导：由 location 得出 ws://<gateway-host>/，无需配置、无 origin 校验问题。 必须显式配置网关地址；跨域握手带 Origin，需网关 gateway.controlUi.allowedOrigins 白名单（每加一个入口域名配一次）。
③ 鉴权 Token 入口 ?token= / #token= 一次捕获，落 sessionStorage（per-tab，绝不可进 localStorage）。 同一套入口参数，但起点是另一个域名——需处理跳转带入 / 回跳时的 token 传递，多一条易错路径。
④ 设备握手 device.ts（ed25519 握手）直接从 @openclaw/gateway-protocol import，网关改握手即编译报错。 同逻辑的 210 行手工副本；网关改握手时前端无感，只能等线上失败。
⑤ 媒体 / 头像 <img src="/avatar/<agentId>"> 同源直出，无需绝对化、无需补 token。 必须 resolveGatewayHttpBase(wsUrl) 绝对化到网关源，且补 token 必须在绝对化之后（顺序错 → token 静默丢 → 401 破图）。
且 /avatar/*、/__openclaw__/assistant-media 无 CORS、OPTIONS 404，只能 <img> / <audio> 直出，探测失败要乐观继续。
⑥ 契约同步机制 编译期：workspace 依赖 + TS 类型检查 + 单测，一次 vue-tsc --noEmit 全覆盖。 无机制：靠人肉比对 + 真机 CDP 冒烟。漂移是「静默失败」，表现为 UI 卡住/空白，而非构建失败。
⑦ 协议版本闸门
（握手硬校验）		 同镜像发布 → 前端与网关声明的 minProtocol / maxProtocol 永远落在同一区间，不存在连接被拒的窗口。 前端独立托管（含浏览器 / CDN 缓存）→ 网关升级协议后， 旧缓存前端会在握手阶段被直接拒绝。网关侧是硬闸门： maxProtocol >= PROTOCOL_VERSION && minProtocol <= PROTOCOL_VERSION （当前 PROTOCOL_VERSION = 4）；不满足即 INVALID_REQUEST / protocol mismatch 并 close(1002)， 源码注释明确写了「stale operator/UI clients cannot enter the v4 surface」。
C 端无法要求用户强制刷新浏览器缓存 —— 这是 B 在本项目最硬的一条风险。 — src/gateway/server/ws-connection/message-handler.ts:813-852 · packages/gateway-protocol/src/version.ts

08 · 选型结论

最终选择：方案 A

前端收敛为 openclaw 仓的 web/ 成员，契约从 packages/gateway-protocol 引入，产物由网关同源托管；逐步退役 agent-claw-web 仓。

判定逻辑：两方案在「能不能跑通」上无差异（B 的 WS 跨域已解决），差异全在 契约能否被机器守护。本项目前端与网关是硬契约耦合（协议 v4 帧结构 / ed25519 握手 / 会话 key 规范形态 / RPC 方法集），今天这个 P0 就是契约漂移的代价—— 用类型把它钉住，比任何流程约束都可靠。

与本次重构动因互为印证：内置 UI 层之所以「改一个积分功能都如此困难」， 根因正是可读性差 + 体量大 + 构建反馈慢；而方案 A 的工程形态（单文件组件、 秒级 HMR、gateway-protocol 统一契约）同时也在为 后续扩展与定制化降低门槛——两条诉求指向同一个选择。

项内容
决定选 方案 A：源码归属 openclaw/web/，契约来自 packages/gateway-protocol
主要依据① 契约可被编译期守护；② 单 PR 前后端协同；③ 同源部署无跨域坑；④ UI 库可开源； ⑤ 面向 C 端：同镜像发布不存在版本 skew；⑥ 零新增接入层与运维成本（复用网关 LB / 证书 / 监控）
面向 C 端的
额外判定		 C 端的两个硬要求是「用户不能遇到功能突然不可用」与「接入层不能多一个故障点」。 本项目的网关对陈旧 UI 客户端是握手硬拒（protocol mismatch → close(1002)， PROTOCOL_VERSION = 4），而 B 的前端在 CDN/浏览器里是缓存态的、无法强制刷新 ⇒ B 在协议演进时会直接产生「旧用户连不上」的 C 端事故。A 把前端打进网关镜像后， 该风险的成因被彻底移除。
重构动因
（本次任务）		 修改「积分」功能时暴露的结构性成本：内置 UI 层 512 文件 / 254,359 行、 单文件最大 2,908 行，一个功能点散落在 32 个文件（11 逻辑 + 21 语言）里 → 定位困难、高度依赖 AI 全量读取（多次崩溃、电脑死机）、改完需重新构建并重装本地插件 → 迭代极慢。重构为 Vue 后：改动点收敛到单个 .vue + store、 Vite 秒级 HMR、文案改动面 21 → 1，维护难度显著下降； 并同时为后续扩展与定制化（增量新增页面 / 局部定制）铺好路。 — 详见 02 节
主动接受的代价① 前端发版跟随网关发布节奏 —— C 端下这意味着改文案也要发网关， 需接受（或把纯静态文案变更合并进同一个发布批次）；
② 前端新功能在全量前会经历灰度窗口，需确认 C 端可接受该窗口内的新旧可见性差异 （可用会话粘性收敛）；
③ 静态资源与 WS 共用网关实例资源，C 端峰值下需把静态资源纳入网关容量预算 （必要时前置 CDN + 回源）；
④ 回滚粒度变粗。
不采用 B 的理由① 1301 行协议副本无 CI 守护（今日 P0 成因）； ② 跨仓协同；③ UI 库为内部包不利于对外；
④ C 端下最致命：前端秒级全量 vs 网关分钟级灰度 ⇒ 混合版本窗口内可能出现 握手被硬拒、页面整体不可用，且无法强制刷新用户缓存；
⑤ 独立域名带来一整条新增接入链路与长期运维成本（DNS / 证书 / CDN / LB / 压测 / 监控）； ⑥ 保留独立仓 = 继续维护两份，与本次「降低维护难度」的目标直接冲突。
