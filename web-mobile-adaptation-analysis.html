01 · ui 层的四层适配机制

ui 层不是「写了几条媒体查询」，而是四层各管一段职责的体系。任何一层缺席，手机端都会坏在 不同的地方 —— 这也是评估 web 侧工作量时最容易被低估的部分。

第 1 层 · 外壳：viewport、PWA、主题引导

三件事都在 index.html 里，且都是「不做就必坏」的：

  • viewport 带 viewport-fit=cover 与 interactive-widget=resizes-content： 前者是刘海屏安全区的前提，后者决定手机键盘弹出时是**压缩内容高度**还是只缩小可视视口 —— 缺了它，输入框会被键盘顶到看不见的地方。— ui/index.html:6-9
  • PWA 元信息：<link rel="manifest" href="/manifest.webmanifest">， 配合样式里的 @media (display-mode: standalone) 让「添加到主屏」后按 App 形态排版。 — ui/index.html:35；ui/src/styles/layout.mobile.css（display-mode 2 处）
  • 主题引导脚本：把 data-theme / data-theme-mode 在挂载前同步写到 <html>，避免首屏闪白/闪黑；移动端状态栏颜色也依赖它。 — ui/index.html:37-95

第 2 层 · CSS 断点体系：一个主文件 + 全站媒体查询

主力是 ui/src/styles/layout.mobile.css（951 行），分四段： 1320px（紧凑桌面）→ 1100px（左侧目录改为 slide-over 抽屉）→ 768px（手机， 含短横屏变体）→ 400px（小屏）。第 2 段的注释写得很直白：“Tablet and smaller: switch the left nav to a slide-over drawer.”— ui/src/styles/layout.mobile.css:5 / 92-93 / 273 / 753

抽屉不是纯 CSS：它靠 .shell--nav-drawer-open 状态类 + .shell-nav-backdrop 遮罩实现，说明「开/关」是一个 JS 状态，样式只负责表现。 — ui/src/styles/layout.mobile.css:108-153

除主文件外，各业务样式表也各自带断点，形成「全局骨架 + 局部降级」的分工。 全仓 @media 统计（按出现次数）：

max-width: 768px11手机主断点：单列、控件收纳、字号 16px
max-width: 600px / 480px / 400px10 / 7 / 5逐级压缩内边距与控件
max-width: 720px / 760px9 / 8局部（面包屑、卡片、表格工具条）

第 3 层 · JS：控件收纳与交互降级

CSS 解决不了「桌面把三个下拉平铺、手机必须收进一个按钮」这类结构差异，ui 用一组 移动控件容器来做：.chat-mobile-controls-wrapper + .chat-controls-mobile-toggle（带 aria-expanded/aria-controls） + .chat-controls-dropdown，把「agent 过滤 / 会话选择 / 模型」三项收进同一个弹层。 — ui/src/pages/chat/chat-responsive.browser.test.ts:151-183

  • 单 agent 时降级为紧凑网格：不渲染 agent 过滤时，会话与模型改为上下两行等高， 有专门断言。— 同文件:1658-1670
  • 侧栏会话表按列优先级渐进隐藏：≤900px 隐藏 Runtime、≤768px 再隐藏 Tokens、 ≤500px 再隐藏 Kind/Updated，但**保留 live 状态**。— layout.mobile.css:806 / 823 / 900
  • 触控目标下限 43.5px：所有移动按钮的宽高都被断言不得小于该值。 — chat-responsive.browser.test.ts:22, 941-953
  • 输入区（composer）三档约束：≤768px 字号强制 16px（防 iOS 聚焦自动放大）、 短横屏下输入区高度 ≤ 视口 38% 且消息区 ≥ 40%、展开态最多 5 行且内部可滚。 — 同文件:1251-1286, 1018-1126, 1320-1415
  • 结果侧栏在手机端变覆盖层：桌面是卡片内滚动，300px 级宽度改为 position: fixed 全屏覆盖并可滚。— 同文件:1706-1739
  • Tooltip 支持触控：长按触发、移动阈值取消，避免手机上 hover 永远出不来。 — ui/src/components/tooltip.ts:192-221

第 4 层 · 测试：视口矩阵 + 几何断言

chat-responsive.browser.test.ts 是这套机制的「防回退网」：对 320×568 / 375×812 / 430×932 / 768×1024 / 1024×768 / 1366×900 / 1440×900 七个视口跑同一批 几何断言（首条消息不被顶栏压住、左右气泡左右对齐、圆角/内边距、桌面控件保持一行、 无横向溢出、弹层不出视口、触控尺寸）。— 同文件:13-21

关键设计：这些断言量的是 getBoundingClientRect（真实几何），不是「有没有某条 CSS 规则」。 所以它既约束了实现，也允许实现方式变化（Lit → Vue 也能照搬）。这是 web 侧可以直接复用的部分。

02 · 断点清单与语义

把 ui 的断点按「屏幕形态」而不是「数值大小」理解，才能判断 web 侧要改哪些位置： 数值只是手段，形态才是要复刻的东西。

形态触发条件要做的事（ui 现状）web 现状

05 · 规模估算与分期

总体判断：中等偏大，但可分期独立上线。合计约 12–18 个文件、2000–3500 行（CSS 为主，新增 JS 状态很少）。 其中 P0+P1（外壳 + 抽屉骨架）就能让手机端**可用**；P2/P3 是体验与细节。
P0

外壳与安全区（手机端能「打得开、看得见」）

index.html viewport / manifest / 主题引导；env(safe-area-inset-*)； 100dvh 高度。3–6 文件，约 100–200 行。 验收：真机（或 320×568 视口）打开对话页，输入框不被键盘遮挡、无横向滚动。

P1

布局骨架 + 目录抽屉（腾出内容宽度）

新增 mobile.css（1320/1100/768/400）；MainLayout 抽屉状态 + 遮罩； ChatSidebar 适配；ChatView 放宽窄屏策略。4–6 文件，约 400–600 行。 验收：320px 下内容占满宽度；点汉堡开抽屉、点遮罩/条目关闭。

P2

对话区交互降级（真正好用）

触控目标、控件收纳、输入区三档、元信息常显、弹层不出视口。2–4 文件，约 700–1100 行 （ChatPane.vue 只做最小条件渲染 + 新增样式）。

P3

数据表格页 + 回归基线

8 个 el-table 视图的列优先级；新增 web/tests/smoke/responsive.e2e.mjs （视口矩阵 + 触控尺寸 + 无溢出）。9–11 文件，约 700–1400 行。

分期之外的依赖关系

  • P1 依赖 P0（没有 100dvh 与安全区，抽屉高度在手机上会算错）。
  • P2 依赖 P1（抽屉占位宽度会改变对话区可用宽度，断点需要一起回归）。
  • P3 与 P2 相互独立，可并行。
  • 回归基线（P3 的后半段）建议**随 P0 一起建**，否则 P1/P2 的每一次调整都只能靠肉眼。

06 · 验收口径（可复用的探针）

ui 的断言方式是「几何 + 视口矩阵」。web 已有 Playwright + 系统 Chrome 的探针基础设施 （web/tests/smoke/*.e2e.mjs），把 ui 的断言逐条翻译过来即可， 不需要引入新的测试框架。

ui 断言web 侧的等价检查出处

触控目标 ≥43.5px枚举移动可见按钮的 getBoundingClientRect()，断言宽高下限 :941-953
手机下拉在视口内打开弹层后断言 x ≥ 8 且 x+width ≤ 视口宽-8 :902-905
输入区短横屏约束568×320 下断言输入区 ≤38% 高、消息区 ≥40% 高、展开态 ≤5 行 :1283-1287, :1018+
移动字号 16px≤768px 断言语 textarea 的 font-size === 16 :1254-1255

建议的新增文件：web/tests/smoke/responsive.e2e.mjs，视口集合沿用 ui 的 [320×568, 375×812, 430×932, 768×1024, 1366×900] 五档起步（既覆盖手机，也覆盖现有桌面基线， 防止「为手机改坏桌面」）。

07 · 风险与待确认

风险（按影响排序）

风险说明缓解
ChatPane.vue 单文件 5917 行 模板/逻辑/样式耦合，移动端条件渲染容易牵动桌面行为（本项目已踩过「v-if 撑破几何」的坑） 样式单独成文件；模板只加最少的分支；每次改动跑现有 5 个 smoke
Element Plus 的桌面语义 el-table/el-dialog/el-select 的默认尺寸、弹层宽度与 teleport 行为都为桌面设计；弹层宽度会反向受宿主宽度影响 统一在 mobile 样式里覆盖，不改组件用法
iOS 键盘与 100vh 不补 interactive-widget 与 dvh 时，键盘弹出会把输入框顶出可视区 P0 前置解决，真机验证
与现有拆分视图逻辑冲突 窄屏「只渲染活动窗格」的策略在手机上要保留还是替换成单窗格，语义需先定 见下方待确认 ①

开工前需要拍板的三件事

  • ① 手机端的产品形态：是多窗格拆分在手机上**彻底禁用**（沿用现状 + 引导文案）， 还是要支持「窗格切换器」（屏幕上只显示一个、用顶部标签切换）？后者要动 ChatView 的布局状态，量级 +约 200–300 行。
  • ② 手机端要覆盖到哪些页面：只保对话页（P0–P2），还是包含 8 个数据表格页（P3）？ ui 是全站都适配，web 若只保对话页可省掉约 1/3 工作量。
  • ③ 是否要做 PWA（manifest + standalone）：不做的话「添加到主屏」体验差，但可省掉 图标资产与 standalone 样式两组工作。
建议 先落 P0 + P1 + 回归基线：这三块决定了「手机能不能用」，且与具体产品形态无关 （①②③ 的答案都不会让它们返工）。P2/P3 待上述三点拍板后按优先级推进。
